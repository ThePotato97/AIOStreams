# Where atmos-render departs from the traced engine

The reference is the traced DAP-VR 8.1.0 engine, its Atmos for Headphones tuning, Windows' encoder
(`DolbyHrtfEnc.dll`) and DD+ decoder (`DolbyDecMFT.dll`), and the Reference Player's OAMD parser
(`dlb_oamdi`): the `dolby-render-parameters.md` and `dolby-atmos-for-headphones.md` notes, through
their second question batch (§10). Everything the renderer does that isn't read from that trace is
listed here: what it does, why, and what would settle it. An entry is added or removed in the same
commit as the code it describes.

`--output speakers` renders for two built-in speakers instead (Dolby Atmos for built-in speakers,
`speaker_render.rs`): the speaker-path trace (`dolby-speaker-render.md`, `renderer.md`,
`virtualizer.md`, `postchain.md`, `profile.md`, 2026-11-08), DAP-VR output mode 11 with Dolby
Access's built-in-speaker settings (speaker angles 10/10/10, height filter off, the 8->2 matrix,
dynamic speaker optimization off) for a stereo endpoint. The speaker path's own entries are
under "Speaker path" below.

`--modes stream` (default) takes each element's render mode from the stream, as the Reference
Player does; `--modes windows` renders everything Near, as Windows does. `--modes far` renders
everything Far, which no Dolby product does: it's the listener's choice (the player's headphone mode
setting), with Far's traced tuning, otherwise as `stream`. Everything else is Atmos for Headphones'
chain in every mode, the Windows encoder's input headroom and the Movie profile's post-processing
(1) included.

## Not implemented

| # | What | Why | Settled by |
|---|---|---|---|
| 1 | Post-processing. **Headphones run the Movie profile's**, the profile for films and TV (`profile_rtp_by_profile.csv`, hp_movie): the volume leveler at amount 4 with in/out targets −20 dB, and volmax, +4 dB as a flat gain before the peak limiter while the leveler is on (leveler.md §7). `leveler.rs` translates the trace's per-block port (`leveler.py::DVLeveler`, engine A) and matches it on 3938 blocks of pink noise through every dynamic path (onset, attack, hold, flux reset, fade, silence) to 1e-9 in every state and 1e-4 dB in the gains; its detector's band powers match the code-translated filterbank's. DAP works a block at a time, so the renderer holds one block (256 samples of latency). Everything else Movie sets is off or inert on headphones [C]: IEQ, dialogue enhancer, regulator, GEQ, bass enhancer, audio optimizer and volume modeler are off; surround boost (96) only touches the speaker virtualizer's surround group; the surround decoder runs on neither path (surround_decoder.md: A's decoder never reads object or bed channels and `stereo_cp_bypass_mode` 1 skips the stereo pair; R's gate needs OAMD == NULL, which the Reference Player never passes); MI is never allocated with `mi_process_disable` = 1. **Not as traced:** (a) the trace's port was checked by reading code only, not against the DLL's output, and two details in it are [I] (leveler.md §11); (b) band gains and volmax are converted to linear with the exact power, where DAP uses its own 2^x routine (`sub_18000E770` for the band gains) [I], the same question as 5a's −14 dB; (c) A puts the stereo-bypass pair in the same band analysis and gives it the same gains as the ears; the renderer measures and gains their sum, which is the same whenever only one is present (a stream is either objects or channel-stereo); (d) **the built-in-speaker output gets none of Movie's processing**: its dialogue enhancer (amount 5) isn't traced, nor surround boost's dB reference (the leveler is off in every speaker profile, so volmax never applies there); (e) the headphone mode setting (As mixed / Near / Far) chooses render distances only; every mode gets Movie, and what post-processing the Reference Player itself runs isn't checked. | (a) no runtime harness for the DLL; (d) untraced; (e) not checked. | (a) the DLL's output on a known signal; (d) the dialogue enhancer's algorithm and surround boost's reference; (e) the Reference Player's DAP-VR runtime parameters. |
| 2 | After Atmos for Headphones, Windows' playback resamples to the device's rate (E's 48 to 44.1 kHz on a 44.1 kHz device) and converts to int16 with dither. | 3 | Sample rates other than 48 kHz. The renderer assumes 48 kHz; a 96 or 192 kHz TrueHD (non-Atmos 7.1 can be) would render at the wrong speed. | A gap of ours. | Resampling, or keeping such sources off the server path. To be fixed. |

| 10 | Channel-based input (TrueHD without Atmos, DD+ without JOC, AC-3, DTS) follows §10's routing in windows mode on headphones and always on speakers (`channels::routed`). **A stereo stream** (FL and FR only) doesn't qualify for Virtual Surround (it opens no more channels than the 2-channel mix), so on Windows it goes into the device pipe's stereo bed. E's `MixChannelBed` / `FoldDownAndMixChannelBed` (0x1800076E8 / 0x180007930) put FL and FR straight into its two stereo-bypass objects: index log2(type) − 1 < 2 selects the object itself. A takes slots 17/18 as **bypass inputs, not objects**: `ConfigureEncoder` builds the list {17, 18}, `CDapVRModule_Prepare` passes it on, and `dapvr_prepare_impl` sets +0x32C8 = 2 and the routing table at +0x32D0. With `stereo_cp_bypass_mode` 1 the pair gets no pan, Off pan, HRTF, room, upmix or virtualizer; it's analysed, scaled ×2⁻³ (A_18002CF70), goes through the main mix's content processing and is summed into output L/R (A 0x18000AEC8). On speakers that's after the virtualizer (post-chain step 6). Its level is traced end to end (stereo_bypass.md): ASAR's bed volume is 1.0, the fold takes FL/FR at 1.0, the bypass objects' +196 is always 1.0, and the −3 dB headroom and ±1 clip belong to `SetAudioObject` alone, so the pair gets neither (`Feed::bypassed`). It reaches each ear or speaker at the output chain's net gain, 1.0005 here (0.99997 with the exact 2^x, 5a), sharing the linked limiter with everything else (`Source::Bypass`). **Wider streams** with a mappable mask (2.1 and 3.0 included) go to Virtual Surround: one static per channel at its Windows encoder slot, Near, LFE kept, never retyped. Stream and Far modes render stereo as two front beds, as before. **Not as traced:** (a) Which channel count and mask the playing app opens is outside the binaries (§10, unverified). This assumes the stream's own; a player that downmixes to stereo itself sends every stream to the bypass. (b) **Streams Virtual Surround can't take** go to the bed too, after Windows' audio engine converts them to the stereo device format. That covers mono (1 channel isn't more than 2), a mask with FLC, FRC, TC, TFC or TBC (TrueHD Lsc/Rsc, Ts, Cvh), and channels a WAVEFORMATEXTENSIBLE mask has no bit for (TrueHD's wides and Lsd/Rsd; how a player opens those is outside the binaries). The engine's coefficients aren't traced (§10 'Not traced'), so these stay per channel at assumed positions: front left/right of centre at x = 0.25/0.75 on the front wall; top centre, top front centre and top back centre at (0.5, 0.5), (0.5, 0) and (0.5, 1) on the ceiling; top sides and wides at their Dolby bed IDs (11/12, 15/16); Lsd/Rsd as the sides. | (a) is outside the binaries; (b) untraced. | (a) a loopback capture, or the format each player opens. (b) AudioEng's downmix and mono upmix to the device format. Also open: where the engine applies app/session volume (taken as 100 %), and the runtime blob's `cp_bypass_mode` (1 from the Dolby Access builder decode, not a captured blob; mode 0, the library default, would upmix and HRTF the pair). |
| 11 | 5.1 surrounds follow the stream's channel mask, as §10's Virtual Surround table does. ## Changed from Cavern (E-AC-3 JOC)

| # | What | Why |
|---|---|---|
| 20 | Each frame's 24 interpolated matrices are computed from that frame's JOC payload and applied in order. Cavern's applier steps its timeslot against the input channel count (7), out of step with frames. | Follows the frame structure. |
| 21 | Smooth two-point interpolation maps parameter bands in both halves; Cavern maps only the second. Steep two-point applies the second matrix from its offset; Cavern never uses it. | Follows the format's logic. |
| 22 | The values follow Windows' decoder: clip gain 2^(x-4)(32+y)/512 on the time-domain downmix, ramped over 256 samples, with the object output x16 and clipped to ±1 (Cavern's gain agrees only when x = 4); dequantisation steps 0.2001953 and 0.1000977, wrapped in integers; at most 15 objects; JOC only on a 3/2 core; the surround stage for configs 3 and 4. | 23 | The core is decoded by an FFmpeg child, not linked libavcodec and not Cavern's decoder (no AHT). | No dependency on one FFmpeg build's library ABI. |
